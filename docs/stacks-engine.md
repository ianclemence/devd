# The stack engine

`devd-stacks` turns "which framework, which tools, which commands" into data. The CLI, the terminal dashboard, the window, the HTTP API and the MCP server are all projections of the same capabilities, so a stack that works in one works in all of them.

```text
 stacks/*.yaml  tools.yaml          (structured, validated at load)
        │
   StackRegistry ── validate: tools exist, options referenced, every command expands
        │
 ┌──────┼──────────────┬───────────────┬────────────────┐
 init   detect         tasks           toolchain
 plan→run→verify   evidence→context   resolve→run/bg   probe→plan→install/service
        └──────────────┴───────────────┴────────────────┘
                capabilities: stacks.* project.* task.* toolchain.*
```

## Capabilities

| Capability | Tier | Purpose |
|---|---|---|
| `stacks.list`, `stacks.describe`, `stacks.schema`, `stacks.matrix` | read | Discover stacks, options (with a JSON Schema), request/plan/report/context schemas, the compatibility matrix |
| `stacks.validate` | read | Resolve a request: issues (`field`, `code`, `message`), exact commands, prerequisites, services |
| `project.init` | exec | Create a project; `dry_run` returns the same plan |
| `project.detect`, `project.import`, `project.list`, `project.forget` | read / write | Understand and register existing projects |
| `project.tasks`, `project.run`, `project.exec` | read / exec | Run the project's own workflow commands |
| `project.run_destructive`, `project.exec_destructive` | destructive, human only | Anything that can destroy data |
| `task.list`, `task.logs`, `task.stop`, `stacks.cancel`, `stacks.log`, `stacks.runs` | read / exec | Background processes, progress, history |
| `toolchain.list`, `.check`, `.plan`, `.status`, `.logs`, `.devices` | read | Probe tools and services |
| `toolchain.install`, `.remove`, `.service` | admin | Change the machine; always need approval |

## Using it

```text
devd new                       guided flow (terminal)
devd new laravel blog --stack-version 12 -o database=pgsql --pm composer --plan
devd stacks list | show <id> | schema | matrix --markdown
devd tools list | check <stack> | plan <tool> | install <tool> | start <service>
devd project detect . | import . | tasks . | run . test | exec . -- php artisan route:list
devd project terminal .             # your terminal in the folder, pinned runtimes and devd first on PATH
```

In the window: **Create**, **Develop** and **Toolchain**. In the terminal dashboard: keys `0` (Create) and `-` (Toolchain). Over HTTP and MCP: the capabilities above, discoverable with `stacks.schema`.

## Adding a stack

Copy a file in `crates/devd-stacks/defs/stacks/` (built in) or put one in `<devd home>/stacks/` (extension). Define versions and their tool requirements, options, the `init.steps` with `{placeholders}`, `verify`, `tasks`, `detect` rules and `exec` policy. Loading validates it: unknown tools, options or placeholders, bad patterns and duplicate ids reject the file with the reason (`stacks.list` reports rejected extensions). Extensions cannot replace a built-in. No Rust changes are needed unless the stack needs a genuinely new step kind.

Step kinds: `exec` (argv, never a shell), `write`, `mkdir`, `env` (upsert dotenv keys), `json` (set values by dotted path), `fetch` (zip from an allow-listed host). Conditions (`when`) test options, plus the engine's `git`, `install`, `package_manager` and `version`.

Every definition records how it was checked (`verified.method`: `cli-help` when flags came from the tool's own help at the stated version, `docs` otherwise). Version differences are modelled as versions with their own requirements; options can be limited to versions. When a scaffolder changes, update the definition and its `verified` line; `docs/stacks.md` is regenerated by `DEVD_UPDATE_DOCS=1 cargo test -p devd-stacks`.

## Security model

- **Argv only.** Commands are argument arrays. User values are never interpreted as shell syntax, and `project.exec` refuses shells and privilege tools.
- **Directories.** Agents work only under the projects root, extra `project_roots` from settings, and projects a person created or imported. People may use any directory except system and home roots. `..` and symlinks are resolved first.
- **Approval.** Installing or removing software and controlling services are `admin`; destructive tasks and commands are `destructive` and human-only. An agent can ask for a plan and a person approves it in the window, dashboard or CLI.
- **Privileges.** Package installs use root or `sudo -n` only. Without either, the plan says so and prints the exact command. Nothing prompts for a password and nothing is piped from the internet into a shell.
- **Secrets.** Output is redacted (`KEY=value`, bearer tokens, URL credentials, common token formats) before it is logged, stored or sent. `.env` values are never read into project context, only names. devd's own tokens are removed from child environments.
- **Network exposure.** Service definitions record bind defaults. devd does not open ports or change service configuration; it starts a service only when nothing else holds its port.
- **Audit.** Every capability call is audited with redacted arguments; each initialisation, task and toolchain change also has a history row and a log (`stacks.runs`, `stacks.log`).
- **Containers** are never required. Docker is a tool like any other.

## Verification

- `cargo test -p devd-stacks` loads and expands every definition, exercises the engine against fixture stacks (no downloads), detection fixtures, agent confinement, approval rules, interface parity (the same plan for CLI, TUI, window, HTTP and MCP actors) and checks that `docs/stacks.md` is current.
- Real scaffolds were run against Go, Rust, Node.js, Flask (pip and uv), Django, FastAPI, Rails, Laravel, Next.js, Vue, React/Vite, SvelteKit, Express, Expo and React Native; each reported `ok` with its checks. Astro and Spring Boot download from GitHub / start.spring.io and Nuxt needs a newer Node.js than the build machine had, so those were verified by validation and command inspection only.
- For a new stack, run `devd new <stack> check-app --dest /tmp/x` and confirm all checks are `ok`.

## Limits

Long operations in the terminal dashboard block its screen until they finish (the window and `devd new` show live progress). Service control needs systemd, SysV `service`, or a tool with a daemon mode; otherwise devd explains what to run. Android emulators need hardware virtualisation the host may not offer; `toolchain.devices` reports what adb sees.
