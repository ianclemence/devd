# The desktop shell

The released desktop application is a Tauri 2 window over the **same** devd
server and the **same** HTML, CSS and JavaScript as `devd ui`. It is not a second
interface and it has no privileged bridge.

```text
devd-desktop.exe
  ├─ capability registry (devd-bootstrap)
  ├─ workspace: project processes
  ├─ loopback HTTP server (devd-server, ephemeral port)
  └─ Tauri webview ──HTTP──> http://127.0.0.1:<port>/
```

## Startup

1. `Bootstrap::discover()` resolves `DEVD_HOME`, opens and migrates SQLite,
   discovers Git, creates the process-owning workspace and registers every
   capability once.
2. A background thread starts a multi-thread Tokio runtime and calls
   `devd_server::serve_with` with port `0`, the shared workspace, and an external
   shutdown receiver.
3. The server binds loopback, chooses an ephemeral port, injects the bearer token
   into the HTML and reports readiness over an in-process channel.
4. The window navigates to that loopback origin. The UI then behaves exactly as
   it does in a browser: it calls the API with the token from the page.

If the backend does not become ready within 30 seconds, or fails to start, the
window shows the real error rather than a blank page.

## Shutdown

Closing the window hides it in the notification area; the process and its
backend keep running, so agents, shares and services are not interrupted by
closing a window. **Quit devd** in the tray menu is the explicit exit: it sends
the shutdown signal, the HTTP server stops accepting, `Workspace` is dropped and
project processes are terminated. The same path runs on `RunEvent::Exit`;
shutdown is idempotent.

## The tray

Right-clicking the notification-area icon opens a menu built from the same
capability API as the window, so every action has the same permissions and the
same audit trail. Left-clicking the icon restores the window (and reloads it only
if it is showing the browser's network-error page).

The menu is rebuilt from live state every thirty seconds instead of being a
startup snapshot:

* the title row names the version, the loopback address, and how many services
  are running or how many incidents are open;
* **Health** lists recent self-healing incidents and what was done, or says
  there are none, and links to Diagnostics;
* **www** lists registered projects, opening each project's folder;
* **Quick Share** lists every open link with its real public address (open or
  stop) and every site that can be shared;
* **Services** names each service's actual state (`running`, `stopped`,
  `running, not answering`), enables Start/Stop/Restart only when they would
  act, and links to per-service logs, install and adoption;
* **Start All** and **Stop All** call the dependency-ordered `stack.up` and
  `stack.down` capabilities, so they never touch a process devd does not own;
* The remaining items are **Quick app**, **Tools**, **Terminal**, **Preferences**,
  the devd and projects folders, the desktop log, **Start at login** and
  **Quit devd**.

Menu handlers return immediately; actions that take seconds (starting the stack,
opening or closing a tunnel, restarting a service) run on their own thread.
A second launch focuses the running window instead of adding a second icon.

## Permissions and isolation

* **No Tauri commands are registered.** The window has only `core:default`
  permissions; there is no shell, filesystem or process plugin. A compromised
  page has no IPC function to call.
* The capability file lists only the `main` window. It has no `remote` entry, so
  the loopback origin — which is remote from Tauri's point of view — cannot
  reach IPC, even if a command is added later by mistake.
* Top-level navigation is allowed only within `http://127.0.0.1:<port>`
  (`localhost` and `[::1]` are also accepted). Any other HTTP(S) URL is opened in
  your browser and refused in the shell. `about:blank` is used only for the
  startup-error page.
* The Preview iframe keeps its existing sandbox. A previewed website is a
  different origin, inside a sandboxed frame, and has no path to the Tauri shell
  or to the native window.
* The bearer token is generated by the server and delivered to the window in the
  HTML over loopback. It is never written to disk, never placed on a command
  line, and never returned by an endpoint.
* The preview continues to use the site's own localhost HTTPS URL. The CA trust
  story is unchanged.

## Getting a working window

A window is not one file. `devd-desktop.exe` loads `WebView2Loader.dll` from the
folder it lives in, so download the portable **zip** (or the installer), not the
standalone `devd-desktop-...exe`. The zip also carries `devd.exe` and
`launch.vbs`; the launcher runs `devd setup` on the first start, then opens the
window.

The published window is Windows x86_64 only today. The same code builds on
macOS; on Linux the server and the web interface are the supported path
(`devd ui`). [`platforms.md`](platforms.md) is the matrix.

If the window does not open:

1. Read `%LOCALAPPDATA%\devd\desktop.log`; the startup error is written there.
2. The window needs the Microsoft Edge WebView2 runtime. It ships with current
   Edge; if it is missing, install it from
   <https://developer.microsoft.com/microsoft-edge/webview2/>.
3. The command line works without the window: `devd ui` serves the same
   interface at a loopback address.

## Building

Requirements:

* Rust 1.77 or newer (the release is built with the `x86_64-pc-windows-gnu`
  toolchain in this repository) and a C compiler for the bundled SQLite.
* WebView2 runtime on Windows 10/11. It ships with current Edge; the installer
  does not bundle a second browser engine.
* Tauri CLI 2 (`cargo install tauri-cli --version "^2"`) only for producing the
  installer. `cargo build -p devd-desktop` produces the portable executable.

```powershell
cargo build --release -p devd-desktop
cargo tauri build --target x86_64-pc-windows-gnu
```

The Tauri configuration points `frontendDist` at `crates/devd-server/ui` so the
bundle uses the same source assets as the server. At runtime the window does not
load the bundled copy: it loads the server's `/` with the token injected.

### Packaging

`cargo tauri build` produces MSI and NSIS bundles under
`target/<triple>/release/bundle/` when the required bundler is available. The
repository's own installer script (`scripts/release-installer.ps1`) builds the
release binaries and compiles `installer/devd.nsi` with NSIS 3, installing
`devd.exe`, `devd-desktop.exe`, `WebView2Loader.dll`, the launcher, shortcuts and
the uninstaller under `%LOCALAPPDATA%\Programs\devd`. The portable zip carries
the desktop executable and the loader DLL together; the executable will not start
without the DLL beside it.

## Running beside the daemon

* **The window is a client of the resident process when there is one.** If
  `devd daemon` is running the window loads the interface that process serves and
  starts no backend of its own, so there is one owner of scheduled work and of
  project processes. With no daemon the window starts its own backend and becomes
  the instance until it closes. See [`daemon.md`](daemon.md).

* WebView2 availability is a Windows prerequisite. On Linux, Tauri uses
  WebKitGTK and must be built on that platform; the release artifacts here are
  Windows.
* The installer is not code-signed. Windows SmartScreen warns once; the published
  SHA-256 verifies the download.
* The Tauri window itself is a webview, so the terminal is still rendered by
  xterm.js rather than a native terminal control. This is deliberate: it is the
  same terminal implementation as the browser surface.
