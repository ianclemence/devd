# v0.2.0 — M1: the application

`devd` now has a window.

This release turns the core into something a person can use without a terminal:
a local application served by the `devd` binary on loopback, opened as a
chrome-less window. It is a **surface, not a second implementation** — the
server is generic over the registry, and the interface is a pure client of it.

```bash
devd ui            # opens the application window
devd serve         # headless: the API alone
```

## What you can do

* **Manage a real repository end to end** — status, per-file diffs, stage,
  unstage, discard, commit, amend.
* **History** — the log, commit inspection, revert, cherry-pick.
* **Branches** — create, switch (with the real overwrite check first), merge,
  rename, delete.
* **Tags and remotes** — create, delete, fetch, pull, push, force-push.
* **Stashes and worktrees** — the full lifecycle.
* **Recover** — conflicts with resolution, the reflog, reset modes, squash,
  bisect, continue and abort.
* **The whole capability registry** — search it, read a declaration, run it.
* **The audit trail** — with plan, applied and refused marked separately.
* **The environment check** — the same one `devd doctor` runs.

`Ctrl+K` opens a command palette backed by the registry's own ranked search, so
it cannot offer an action the CLI cannot perform.

## Approvals are tokens, not booleans

The naive design is `POST /api/invoke { "approve": true }`, which makes the
approval something the *client* asserts. That is the exact property this product
exists to prevent, so it is not what was built.

```
POST /api/invoke { id, args }
  → { approval_required: true, plan: {…}, token, expires_in_ms }   changes nothing

POST /api/approve { token }
  → applies the server's own stored arguments
```

What was displayed and what executes cannot differ, because the executing
arguments never came back from the client. A token is single-use, expires in 120
seconds, is bounded to a fixed number of pending decisions, and is bound to the
capability, the arguments and the actor.

`POST /api/deny` dispatches with `Approval::Denied`, so a refusal is recorded
rather than invisible. The server also forces the actor to `human:http`: a
caller cannot claim to be an agent to escape a restriction, or a human to unlock
an agent-only path.

## Loopback hardening

A web page the user has open can send requests to `http://127.0.0.1:<port>`. It
cannot read our responses, but it can send. Four defences, in the order they are
applied:

| Defence | Result |
| --- | --- |
| `Host` allow-list (`127.0.0.1`, `localhost`, `[::1]`) | `403` — defuses DNS rebinding |
| Every `OPTIONS` refused | `405` — no preflight can complete |
| Foreign `Origin` | `403` |
| 256-bit bearer token, constant-time compare | `401` without it |

The token is generated at startup, injected into the served page, never written
to disk, and returned by no endpoint.

## Shared environment checks

The doctor checks moved into `devd-core::doctor`, so the CLI and the window
report the same thing from the same code. A held port — 80 and 443 usually are,
on a developer machine — is reported as `info`, not as a failure.

## Fixed

* A failed Git command that wrote its reason to **stdout** (which `git commit`
  does: "nothing to commit, working tree clean") reported an empty message.
  It now reports what Git said, and says so explicitly when Git said nothing.
* `Store::open_in_memory()` now migrates, so an in-memory store is usable
  immediately instead of failing every table read.

## Tests

**148 tests pass** (up from 98), zero warnings:

* `devd-server` unit — 17, covering the approval store (single use, expiry,
  capacity, binding to capability and arguments) and the request guards.
* `devd-server` HTTP — 22, driving the real router: the four loopback defences,
  the token requirement, capability search and description, an approval-gated
  invocation that changes nothing until approved, a decline that is audited and
  applies nothing, token replay, and the error envelope.
* `devd-cli` — 4, including port selection.
* `devd-core` — 47, `devd-git` — 12 unit, 30 lifecycle, 16 policy.

The loopback matrix and the Git approval flow were also exercised against the
release binary on a socket; the observed results are in
[`docs/app.md`](https://github.com/ianclemence/devd/blob/main/docs/app.md#what-was-actually-observed).

## Still not built

The TUI and the MCP server. Services, sites, runtimes, DNS and TLS — the panels
say so rather than offering controls that do nothing. The window is a browser
engine in application mode, not a native shell; Tauri is the intended eventual
wrapper and the interface does not change when that happens.

## Install

```bash
git clone https://github.com/ianclemence/devd.git
cd devd
cargo build --release
./target/release/devd ui
```

Requires Rust and `git` on `PATH`. This release ships source archives only; it
contains no third-party binaries.

See [`CHANGELOG.md`](https://github.com/ianclemence/devd/blob/main/CHANGELOG.md)
for the full list and [`docs/limitations.md`](https://github.com/ianclemence/devd/blob/main/docs/limitations.md)
for the honest gaps.
