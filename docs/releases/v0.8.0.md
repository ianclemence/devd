# v0.8.0 - persistent agents, project processes, shared state and a native shell

devd now finishes the v0.7 roadmap. The agent you run in the window keeps running
when you leave the window, a coordinating agent can delegate to a second real
process, a project can declare its processes in `devd.yml`, people and agents
share durable notes and todos, and devd itself is a native desktop application.

## Sessions that survive the window

Run Claude Code, OpenCode or a shell, switch to Preview, open another section,
switch tabs, or reload the entire page. The PTY is owned by the backend, so the
harness does not restart and the terminal reattaches to the same process.

Every session has a stable id, a harness, a project directory, a pid, terminal
dimensions, lifecycle state, exit code, timestamps and a bounded transcript.
The session list survives relaunching devd, and a running session can be resumed.
Completed and failed sessions stay readable.

The states are honest. A PTY cannot survive the process that opened it, so a row
left by a dead devd process is `stale`, not `running`; a row owned by another live
devd process is `unavailable` and says which process owns it.

## More than one terminal, and real delegation

Sessions are independent processes with tabs, rename, stop, dismiss and transcript
replay. **Delegate a task** starts a second agent as a genuine child process,
gives it a working directory and instructions, and lets the coordinator wait,
inspect the result, or cancel it.

The limits are deliberate: eight unfinished tasks, three levels of nesting, a
900-second wait and a task timeout. A wait timeout does not kill the child. The
child's own permission prompts remain the authority; devd does not approve them
and does not type into a person's terminal.

## `devd.yml`

A project can declare the processes it needs:

```yaml
version: 1
project:
  name: example-app
processes:
  web:
    command: ["npm", "run", "dev"]
    working_dir: "."
    health:
      url: "http://127.0.0.1:3000/"
  worker:
    command: ["npm", "run", "worker"]
    depends_on: ["web"]
```

The manifest is executable configuration, so devd validates it, shows the exact
commands, and runs nothing until a human approves the semantic hash. Editing the
manifest invalidates the approval. Commands are argv arrays, working directories
stay inside the project, health checks are loopback-only, and the process
environment is explicit rather than inherited from the daemon.

Start, stop, restart and start-all are supervised. Logs, pids, exit codes,
restart counts, health and the last failure are visible in **Processes**, and a
failure includes the last output line.

## Shared notes and todos

**Shared** holds project-scoped scratchpads and structured todos. They are not
chat history: they survive agent sessions, window reloads and application
restarts, and the same capability API is used by people and agents.

Scratchpads have authors, timestamps and revision numbers, so a stale edit is a
conflict rather than a silent overwrite. Todos have status, priority, assignee,
task association and transition history. An agent can append a finding, create a
todo for another agent, spawn it, wait, and update the todo with the actual
result.

## A native window

`devd-desktop` is a Tauri 2 window over the **same** server and the **same**
HTML, CSS and JavaScript. The backend starts in-process on an ephemeral loopback
port; the window loads the UI exactly as a browser would.

No Tauri commands are registered. There is no shell, filesystem or process plugin.
The capability file names only the main window, and remote origins - including a
previewed website - have no IPC access. Top-level navigation away from devd is
refused and handed to the system browser. Preview keeps its sandbox and localhost
HTTPS behaviour.

## How it is wired

| Piece | What it does |
| --- | --- |
| `devd-workspace` | PTYs, child watchers, delegated tasks, `devd.yml`, project supervision, shared state |
| `devd-bootstrap` | The one registry + runtime composition used by the CLI and desktop |
| SQLite schema 2 | Sessions, tasks, processes, approvals, scratchpads, todos and todo history |
| `session.*` / `agent.*` / `project.*` / `scratch.*` / `todo.*` | Capabilities visible to the window, CLI and MCP |
| Tauri 2 | Native window, no privileged IPC, same UI |
| `/api/sessions` and friends | Session transport; `/api/terminal/*` remains as a v0.7 alias |

## Security

* Only the process that owns a PTY may write, resize or stop it.
* Terminal input, resize, rename and dismiss are human-only capabilities.
* `project.approve` is human-only; start and restart require a matching manifest
  hash.
* Project processes receive an explicit environment and do not inherit devd's
  credentials. Secret-looking declared values are redacted from log reads.
* The loopback bearer token, host allow-list, origin check and approval-token
  model are unchanged.
* The desktop shell exposes no privileged commands to the page.

## Known limitations

* A PTY cannot be reattached after the devd process that owns it exits. The row
  becomes `stale` and its transcript remains readable.
* MCP is a separate process, so an agent-spawned session is owned by that process
  and cannot be attached from the window. It is still a real process.
* A project process is owned by the process that started it. A second devd reports
  it as supervised elsewhere rather than adopting it.
* The Windows installer is not code-signed and the native window needs the
  WebView2 runtime that ships with current Edge.

## Install

Windows: run `devd-setup-0.8.0.exe`. The installer includes the native desktop
application and the CLI. The portable `devd-desktop-v0.8.0-x86_64-pc-windows-gnu.exe`
also runs on its own. Both are listed in `SHA256SUMS.txt`.
