# Write the project guide

A project's guide (`AGENTS.md`, or `CLAUDE.md`) is read at the start of every conversation about the project, so every line costs tokens on every turn and is obeyed as if the person wrote it. Write the lines that earn that, and no others.

## Find out first, from the project

Do not write from what projects of this kind usually do. Read:

- `project.detect` and `project.tasks`: the real commands for install, test, lint, build and run. Run the test command once so the guide says what actually passes.
- The last 30 commits (`git.log`): the commit style, what breaks often, what gets reverted.
- The existing guide, if any, and any rules files in the project (`.cursorrules`, `.devd/instructions.md`). Fix and trim them; do not stack a second copy beside them.
- The code itself: where decisions live, and what looks wrong but is deliberate.

## What belongs

- **How to run it.** The exact commands, and the one that proves a change works. If the tests need a service started or a variable set, say so.
- **Constraints that are not visible in the code.** A folder generated by a tool and never edited by hand. A rule that the database must not be touched in tests. The reason a strange-looking pattern exists, so no one "fixes" it.
- **Traps.** The thing that fails silently, the file that must change with another, the command that looks safe and is not.
- **Conventions that differ from the default** for this language and framework. Not the defaults.
- **What not to do here**, with the reason in a clause.

## What does not belong

A description of each folder (an agent can list it). A summary of the framework. Anything the compiler, a linter or a formatter already enforces. Advice that would apply to any project ("write clean code", "add tests"). Status, plans, a changelog, or anything that will be wrong in a month. A paragraph where a line would do.

## Shape

Short: a screen or two. Plain statements, the reason in a clause where it is not obvious. Commands in code. Put the thing a person gets wrong most often first.

## Check it

Read it as someone who has never seen the project: would a line change what they do? Cut the ones that would not. Then follow it yourself: run the commands as written. A command in the guide that does not work is worse than no guide.
